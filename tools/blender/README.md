# Blender asset pipeline

Every 3D asset, texture and icon the client loads is generated by headless
Blender scripts from code and data in this repository. Nothing is modelled by
hand in a `.blend` file: the scripts are the source, and their output in
`client/public/assets/` is a build product (gitignored, never committed).

Most contributors never need Blender: `bin/dev` downloads the published asset
release that matches the checkout (see [Asset releases](#asset-releases)).
You need Blender only to change art, or to build assets for a fork whose art
differs from a published release.

Run every command here from the repository root.

## Getting the assets

`client/scripts/prepare.mjs` runs before `npm run dev`, `build` and
`typecheck` in `client/` (and `bin/dev` runs it first). It makes
`client/public/assets/` match the checkout:

1. If the folder was already built or fetched for this checkout's
   fingerprint and every step's output exists, it does nothing.
2. Otherwise it downloads the published asset release for the fingerprint.
3. If there is no release, it builds the stale steps with the pinned Blender.
4. If it cannot build either (no Blender, another Blender version, MPFB
   missing for the character step, or a failed step), it prints a warning
   saying why and carries on. The client then uses whatever assets are there
   and draws greybox stand-ins (simple shapes for characters, furniture and
   rooms) for anything missing; with no assets at all there is no castle.

Force one way or the other:

```sh
bin/dev                   # the default (SHS_ASSETS=auto): fetch, else build, else stand-ins
bin/dev --fetch-assets    # only download the release (SHS_ASSETS=fetch); fail if there is none
bin/dev --build-assets    # only build with the pinned Blender (SHS_ASSETS=build); fail if it cannot
bin/dev --skip-assets     # skip the asset step (SHS_SKIP_ASSETS=1)
```

The same variables work with `node client/scripts/prepare.mjs` directly.

## Pinned Blender and MPFB

The build is pinned to one Blender and one MPFB version, and optionally one
basisu version:

| Pin file | Tool | Required for |
| --- | --- | --- |
| `BLENDER_VERSION` | Blender major.minor (`5.2`) | every build step |
| `MPFB_VERSION` | MPFB, the MakeHuman Plugin For Blender (`2.0.18`, with the zip's `url` and `sha256`) | the character step (and so the icons and spell effects, which read its output) |
| `BASISU_VERSION` | basisu, the Basis Universal KTX2 encoder (`2.50`) | optional locally; required to publish a release |

**Blender.** Download 5.2 from https://www.blender.org/download/ (every 5.2.x
release is at https://download.blender.org/release/Blender5.2/). The build
runs `blender` from `PATH`, or `$BLENDER` if set (for example
`BLENDER=/Applications/Blender.app/Contents/MacOS/Blender` on macOS).
`prepare.mjs` checks `blender --version` before running any step, and every
build entry script and test runner calls `pins.require_blender()`, refusing to
build on another major.minor.

**MPFB** (GPL code, CC0 assets) provides the base mesh, targets and rig of the
characters. Install it once per checkout into `.blender-user/` at the
repository root (gitignored), so your normal Blender configuration is not
touched:

```sh
tools/blender/install_mpfb.sh               # download the pinned zip (about 46 MB), check its sha256, install
tools/blender/install_mpfb.sh --zip FILE    # install from a copy of add-on-mpfb-v2.0.18.zip you already have
tools/blender/install_mpfb.sh --check       # is the pinned version installed?
BLENDER_USER_RESOURCES=$PWD/.blender-user \
  blender -b --factory-startup --python tools/blender/pins.py   # check both pins
```

`prepare.mjs` and `build_art_blends.sh` point Blender at `.blender-user/`
automatically when it exists (set `BLENDER_USER_RESOURCES` to use another
folder). The first character build fills a MakeHuman cache in
`<user resources>/mh_cache`. Keep a copy of the pinned MPFB zip: the
characters can only be rebuilt exactly with that version, and
`install_mpfb.sh --zip` installs it if extensions.blender.org stops serving it.

**basisu** encodes the castle textures and portrait backdrops to KTX2.
Without it those steps write PNG only, which the client also loads, and
`prepare.mjs` warns. It is looked up as `$BASISU` (an empty value turns it
off), else `/opt/homebrew/bin/basisu`, else `basisu` on `PATH`. Install it
from https://github.com/BinomialLLC/basis_universal/releases, or on macOS with
Homebrew (`brew install basis_universal`).

`node client/scripts/assets.mjs tools` reports what is installed against the
pins.

**Changing a pin.** Edit the pin file (for MPFB all three lines, from
https://extensions.blender.org/add-ons/mpfb/versions/), rebuild everything and
review the results. A pin is a build input of the steps it affects, so the
asset fingerprint changes with it.

## Asset releases

An asset release is a published archive of `client/public/assets/` for one
**fingerprint**, so contributors without Blender can download instead of
building.

### Fingerprint

The fingerprint is a sha256 (first 16 hex digits) over the path and content of
every build input: every source of every step in
`client/scripts/asset-steps.mjs`, which covers the Python modules each step's
script imports (followed transitively), the `data/` files they name, the
committed sources under `art/`, the pins and `asset-steps.mjs` itself. Tests,
docs (`*.md`), licences, dot folders and gitignored files are left out, and
text is hashed with CRLF read as LF so every clone agrees. Tools no step runs
(`install_mpfb.sh`, `build_art_blends.sh`, the review renders and checks) are
not inputs, and neither is `prepare.mjs`.

```sh
node client/scripts/assets.mjs fingerprint          # this checkout's fingerprint
node client/scripts/assets.mjs fingerprint --list   # with every input and its hash
```

A complete build or fetch writes it to
`client/public/assets/assets-fingerprint.txt`.

Each step is rebuilt when one of its sources is newer than its output. If no
step is stale but the folder records a different fingerprint (or none: a
deleted source, files copied with old times, an interrupted build),
`prepare.mjs` rebuilds every step rather than stamp the new fingerprint on
assets it did not build. Without the pinned Blender it changes nothing and
keeps looking for a matching release.

### Where releases live

A release is `assets-<fp>.tar.gz` (all of `client/public/assets/` except
`ktx2/`, the KTX2 decoder that `prepare.mjs` builds from `node_modules`) plus
`assets-<fp>.tar.gz.sha256`, attached to a GitHub Release tagged
`assets-<fp>`:

```
https://github.com/<owner>/<repo>/releases/download/assets-<fp>/assets-<fp>.tar.gz
```

`prepare.mjs` looks in the first of these that is set:

1. `SHS_ASSETS_URL`: an http(s) or `file://` URL, or a local folder, with the
   same `assets-<fp>/assets-<fp>.tar.gz` layout. An empty value turns
   fetching off (CI does this).
2. The `"repository"` in the root `package.json`, when it is on GitHub. It
   names `github.com/philipqnguyen/spellhollowschool`, so clones and forks
   download the project's published releases by default.
3. The `origin` git remote, when it is on GitHub.

`node client/scripts/assets.mjs release-url` prints the result. A download is
checked against the published sha256, every archive entry must be a plain
file or folder under `assets/`, and it is unpacked beside the old folder and
then swapped in (the `ktx2/` decoder is kept). A download that receives
nothing for 60 seconds (`SHS_ASSETS_IDLE_SECONDS`) is abandoned, and the
default mode goes on to build.

A fork that changes any asset input has a new fingerprint for which the
project publishes no release: it builds with Blender, publishes its own
releases (point `"repository"` at the fork), or serves a folder through
`SHS_ASSETS_URL`.

### What `prepare.mjs` does, by `SHS_ASSETS`

| `SHS_ASSETS` | Fingerprint matches and every output exists | Otherwise |
| --- | --- | --- |
| `auto` (default) | nothing | download the release; if there is none, build the stale steps; if that cannot run or fails, warn and continue with stand-ins (exit 0) |
| `fetch` (`bin/dev --fetch-assets`) | nothing | download the release, or exit 1 |
| `build` (`bin/dev --build-assets`) | the incremental build (nothing when no step is stale) | build the stale steps, or exit 1 |

`SHS_SKIP_ASSETS=1` skips all of it.

### Credits and licence in the assets

Every release contains `assets/CREDITS.md`,
`assets/LICENSE-CC-BY-SA-4.0.txt` (the characters and hair) and
`assets/LICENSE-MIT.txt` (everything else, generated from MIT code and data),
written from `data/credits.json` by
`client/scripts/credits.mjs` when `assets.mjs pack` packs the release.
`prepare.mjs` also (re)writes them after every build or fetch, so a release
published before they existed gets them too. Neither file, nor
`data/credits.json`, is a build input: changing the credits never changes the
fingerprint (they are written after the release's sha256 is checked).

### Publishing (maintainers)

After a change to any asset input lands on `main`:

```sh
npm run assets:publish                 # clean build of HEAD in a temporary worktree, pack, upload
npm run assets:publish -- --reuse      # pack this checkout after an incremental build (inputs must be committed)
npm run assets:publish -- --pack-only  # stop after packing into .out/asset-releases/assets-<fp>/
```

Publishing requires all three pinned tools, so a release is complete
(`node client/scripts/assets.mjs tools --strict`), and the GitHub CLI (`gh`)
signed in. Before building it computes HEAD's fingerprint and stops if that
release already exists, if HEAD is not pushed, or if `gh` is missing. It then
runs `gh release create assets-<fp> ... --latest=false` against the
repository `prepare.mjs` downloads from (`node client/scripts/assets.mjs
release-repo`). Without a git remote it stops after packing; test the packed
folder with:

```sh
SHS_ASSETS_URL=$PWD/.out/asset-releases SHS_ASSETS=fetch node client/scripts/prepare.mjs
```

CI's `asset-release` job (`tools/assets/check-release.sh`) fails on every push
and pull request whose fingerprint has no published release. Releases are
keyed by content, so publishing from the pull request branch before merging is
fine; then re-run the job.

## The build steps

`client/scripts/asset-steps.mjs` lists the steps in order; `prepare.mjs` runs
the stale ones. Each writes under `client/public/assets/`:

| Step | Script | Output |
| --- | --- | --- |
| Castle textures | `castle_kit/textures.py` | `world/textures/` (`textures.json`, PNGs, `_lo` half-size copies, KTX2) |
| Castle cells | `greybox.py` | `world/<cell>.glb`, `world/manifest.json` (also the grounds, the Flying Pitch, the far silhouette `hlod.glb` and the foliage kit) |
| Talking portraits | `npcs/build_portraits.py` | `npcs/` (frames, painted backdrops, `manifest.json`) |
| Furniture | `world/build_furniture.py` | `furniture/<name>.glb`, `furniture/manifest.json` |
| Dorm rooms | `world/build_dorms.py` | `instances/<layout>.glb`, `instances/manifest.json`, `world/instances.json` |
| Class and arena rooms | `world/build_school.py` | `instances/` rooms, `instances/school.json`, class plant props |
| Wishing Rooms | `world/build_wishing_room.py` | `instances/lost_property_vault.glb`, `instances/wishing_room_gathering.glb` |
| Landing rail | `world/stair_rail.py` | `instances/props/stair_rail.glb` |
| Owl | `world/owl_prop.py` | `instances/props/owl.glb` |
| Conjured birds | `volucra/build_birds.py` | `volucra/` |
| Characters | `characters/build_characters.py` | `characters/`, `gear/`, `hair/` (the slow step, several minutes) |
| Icons | `icons/render_icons.py` | `icons/<id>.png`, `icons/manifest.json` (after the characters: clothing icons use the fitted clothing) |
| Spell effects and wand | `vfx/build_vfx.py` | `vfx/` (after the characters: the wand attaches to the hand socket) |
| Guardian animals | `guardian/build_guardian.py` | `guardian/` |

`prepare.mjs` also builds `ktx2/`, the self-hosted Babylon KTX2 decoder, from
`node_modules` (no Blender needed; not part of a release).

Run one step by hand with the same command line `prepare.mjs` uses, for
example:

```sh
blender -b --factory-startup --python tools/blender/greybox.py -- \
    --layout data/world/layout.json --out client/public/assets/world
blender -b --factory-startup --python tools/blender/world/build_furniture.py
blender -b --factory-startup --python tools/blender/world/build_dorms.py -- --furnish
```

Order matters where one step reads another's output: textures before the
cells and rooms, furniture before `build_dorms.py --furnish`, characters before
icons and effects. The character step takes most of a full build's time.

## The castle: layout to greybox

`data/world/layout.json` is the castle the server and client both use: a set
of axis-aligned walkable rectangles (`sim_core::layout::Layout`) with floors,
stairs, doors, spawns, landmarks and interactables. `greybox.py` turns it into
geometry; `data/world/props.json` adds visual props (the server never reads
it).

```sh
blender -b --factory-startup --python tools/blender/check_layout.py -- --layout data/world/layout.json
```

### Layout rules

`check_layout.py` (also run inside `greybox.py`) enforces:

- unique ids, `min < max`, cell ids matching `[a-z0-9_]+` (they become file names);
- stairs carry `y_top` and `rise`; only stairs and grounds slope; stairs are no
  steeper than 45 degrees and keep 2 m headroom under a flat ceiling;
- surfaces overlap in plan only when stacked at least 2 m apart, and whatever
  is drawn under the upper one leaves at least 2.4 m above the lower one
  (`OVERHEAD_CLEARANCE`, the tallest character with a hat);
- a roof slab (ceiling + 0.6 m) never rises through the floor above;
- each door joins at least two surfaces through openings at least 1 m wide;
- every surface is reachable from a spawn. Two surfaces connect where their
  footprints overlap or share an edge (not just a corner) and their heights are
  within the step height (0.35 m) somewhere on that contact, the same rule as
  `sim-core`;
- house-gated rooms are reachable by their own house from a spawn, public space
  never needs a gate, every interactable has a standing spot within its
  radius, and unconnected surfaces at walking height are more than 0.1 m apart.

Conventions: 9 m floor to floor, 8.4 m corridor ceilings (the 0.6 m roof slab
brings the roof exactly to the next floor), 1.5 to 2 m gaps between rooms
that doors bridge (the wall thickness), and floors tiled around solid stairs
so the space under a stair is not walkable.

### How geometry is derived

`layout_lib.Planner` plans everything as polygons; `greybox.py` makes meshes.

- **Floors**: one quad per surface (sloped for grounds).
- **Stairs**: a tread per ~16 cm riser, straddling the walkable ramp. A stair
  beside a floor is solid to its base; a flight over a void gets a stringer.
- **Walls**: per plan line, each surface contributes *air* (floor to ceiling)
  and wants a *wall span*. A face is emitted where one side wants a wall and
  the other has no air, so doors, stair tops and landings cut openings
  automatically, with a header above any opening lower than the room.
- **Railings** (1 m) where a floor ends at a drop.
- **Ceilings and roofs** at `y + ceiling` and 0.6 m above; coplanar ceilings
  are emitted once and roofs under a floor are dropped.
- **Exterior shell**: outer faces and top caps for walls seen from outside;
  rooms less than 3.2 m apart share one wall mass; floating upper storeys are
  extended to the ground so the massing reads as solid.

`layout_lib.find_z_fighting` and `degenerate_polygons` must both be empty for
the real layout (the tests check).

### Materials and outputs

Un-kitted cells use flat-colour greybox materials named by role (`floor_room`,
`wall`, `wall_exterior`, `ceiling`, `roof`, `railing`, `trim`, `prop_*`, ...),
defined in `layout_lib.MATERIALS` from the castle palette
(`world/palette.py`). Walls, trim and grass carry `COLOR_0`, a painted value
ramp the client multiplies into the base colour. UV0 is a world-space planar
projection at 2 m per UV unit.

- `world/<cell>.glb`: Y-up, metres, single-sided, one mesh per material, so a
  cell costs one draw call per material it uses. Stale files of removed cells
  are deleted on each run.
- `world/manifest.json`: every cell's `id`, `file`, `bounds`, `level`, its
  `lights` (point lights, strongest first), and for kitted cells their
  visibility set (`sees`), seats, LOD groups and fires. The client reads it to
  stream cells; `docs/art/castle-kit.md` documents the kitted cells' fields.

The grounds, the Flying Pitch and the far castle silhouette are built by
`greybox.py` through the hooks in `world/outdoor.py`
(`world/grounds_export.py`, `world/pitch_export.py`, `world/hlod_export.py`);
trees and hedges come from `world/foliage.py` and are exported as
`foliage_kit.glb`.

## The castle kit

`castle_kit/` dresses the cells listed in `data/world/castle_kit.json` with
tiling stone, trims, vaults, arches, windows, furniture and props; every other
cell exports as plain greybox. The full reference (grid, schema, pieces,
materials, budgets) is [docs/art/castle-kit.md](../../docs/art/castle-kit.md).

- `grid.py`: grid constants, the bay solver, piece names, face tags, UV
  formulas and budgets (pure Python).
- `schema.py`: validates and resolves `castle_kit.json`.
- `pieces/`: the piece registry (`pieces.build(name, **params)`) by family.
- `rules.py`: a kitted cell's placements from its plan (deterministic).
- `assemble.py`: builds and merges the placements into one mesh per material,
  plus the camera collider and LOD lists.
- `slice.py`, `shade.py`: edge loops and the baked per-vertex ambient
  occlusion (one grey value in `COLOR_0`).
- `textures.py`, `trim.py`, `portraits.py`, `tapestries.py`, `props_atlas.py`:
  the shared `castle_*` texture library, painted from
  `data/art/castle_textures.json`.
- `fire.py`: animated fire markers (the client draws the flames).
- `visibility.py`: each cell's `sees` set.
- `lint.py`: checks on the built cells (intrusion, door and overhead
  clearance, coverage, z-fighting, UV ranges, budgets).

Rules for kit code:

- **Colours come from palette data only.** Pieces name props-atlas colours
  by palette name (`kit:<tile>:@<name>`); the names live in
  `castle_textures.json` `palette`, and `props_slots` rows are append-only
  (their indices are baked into exported UVs). A test fails on any `#RRGGBB`
  literal in piece, rule or assembly code.
- Builds are deterministic: identical inputs give byte-identical files.

```sh
python3 -I tools/blender/castle_kit/schema.py                 # resolved placements
python3 -I tools/blender/castle_kit/lint.py [--cells <id>] [--json]
python3 -I tools/blender/castle_kit/visibility.py --world client/public/assets/world
blender -b --factory-startup --python tools/blender/castle_kit/textures.py -- \
    --out client/public/assets/world/textures [--contact .out/contact] [--no-ktx2]
```

**KTX2.** `textures.py` writes every PNG and then encodes each to KTX2 next to
it, ETC1S for stone, floors and wood and UASTC for trim, glass, banners and
atlases (per material in `castle_textures.json` `materials.<m>.ktx2`). The
PNGs stay the source and the client's fallback. Encoding is deterministic, and
orientation is top row first (the client loads with `invertY: false`).

## Rooms, furniture, props, icons and effects

**Instance rooms** (dorms, classrooms, the duel arena, the Wishing Rooms) are
built like cells and exported to `instances/<layout id>.glb`, with entries
merged into `instances/manifest.json` and `world/instances.json` (cells,
lights in order of importance, ambient, seats). Their walkable layouts in
`data/world/instances/` are generated from the room models (see
[Generated data files](#generated-data-files)). Kit-built rooms
(`world/instance_kit.py`, `world/class_rooms.py`) use castle-kit pieces with
the castle textures embedded.

**Furniture** (`world/build_furniture.py`, models in
`world/furniture_models.py`): every catalog furniture item in
`data/items/catalog.json` as `furniture/<name>.glb`, one mesh, one material,
one draw call. The base colour is a shared atlas and `COLOR_0` is a dye mask
(R primary, G secondary, B trim, black undyed); the client computes
`albedo = baseColor * (1 - r - g - b + r*P + g*S + b*T)` with the item's three
palette colours. Floor and table items have their origin at the bottom centre
of the footprint facing +Z; wall items at the bottom centre of their back.

**Icons** (`icons/render_icons.py`): a 128 x 128 transparent PNG for every
catalog item at catalog default dyes, clothing on an invisible mannequin,
furniture from its model, everything else from `icons/icon_models*.py`.
`--ids 101,3301` renders a few; `--sheet <dir>` writes contact sheets.

**Spell effects** (`vfx/`): `vfx/effects.glb` holds every effect as a node
`spell_<spell id>_<role>`, sharing one unlit, alpha-blended material (draw
additively); `vfx/wand.glb` is the wand (`vfx_models.py` `wand_mesh`: about
35 cm, a carved handle with a pommel, a gold collar and a tapering shaft,
under 400 triangles, origin at the grip and the tip `WAND_TIP` up +Y);
`vfx/manifest.json` maps spells to nodes and colours and gives the wand's
attach transform per body. The client draws the wand in the right hand only
while a character casts or holds it out (docs/architecture.md, "Spells and
dueling").

**Talking portraits** (`npcs/`): frames per canvas size, painted backdrops and
their placements on the castle walls (`data/npcs/portraits.json`).

**Fire**: a burning piece, room or model lists its flames (`fires`,
`candles`) instead of modelling them; they are exported as `fire` entries in
the manifests and node extras, and the client draws and animates them.

**Solids**: `world/solids.py` measures the furniture and props a character
cannot walk through off the pieces' own geometry, and writes them into the
layouts.

## Characters

`characters/` builds the two base bodies, the rig, the animations, the hair
styles of `data/characters/creator.json` and every clothing item of
`data/items/catalog.json`, all from code. The specs are in
[docs/art/](../../docs/art/): `base-body-spec.md`, `garment-shapes.md`,
`character-adoption.md`, `character-look.md` and `style-guide.md`.

The bodies are MakeHuman meshes (MPFB, CC0 assets) shaped by the baked shape
targets in `art/characters/shape_targets/`, which carry the proportions of two
CC BY 4.0 sculpts (credits in [art/CREDITS.md](../../art/CREDITS.md)). The
sculpts themselves are only needed to re-bake the targets
(`characters/wrap_sculpts.py`). Hair is built from the committed source meshes
in `art/characters/hair_meshy/`; the walk and run are retargeted from
Quaternius's Universal Animation Library (CC0, `characters/ual/`).

```sh
# Everything (both bodies, hair, clothing), as prepare.mjs runs it
BLENDER_USER_RESOURCES=$PWD/.blender-user \
blender -b --factory-startup --python tools/blender/characters/build_characters.py -- \
    --assets client/public/assets --no-blend

# Part of it: one body, some items, no .blend, faster animation bake
blender -b --factory-startup --python tools/blender/characters/build_characters.py -- \
    --bodies body_b --only gear --items gear/hat/pointed_a,hair/long_bangs --no-blend --fast

# Review sheets
blender -b --factory-startup --python tools/blender/characters/render_characters.py -- \
    --assets client/public/assets --out art/renders/characters [--only bodies,faces,outfits,poses,anims,hair]

# Tests (the asset tests skip until something is exported)
blender -b --factory-startup --python tools/blender/characters/tests/run_tests.py -- --assets client/public/assets
```

Partial runs merge into the existing manifest. Without `--no-blend` the build
also saves `art/characters/<body>.blend` for inspection.

Checks: `check_characters.py` and `check_garment_shapes.py` (clipping and
layering in test poses at minimum, default and maximum height),
`check_seating.py` (seated, floor and broom clips against seats, floors and
desks), `check_hair.py`, `check_hair_hats.py` and
`check_hair_see_through.py` (hair in motion, under hats, and background
showing through). `prepare_hair_meshy.py` and `measure_hair_guides.py` are
run by hand to remake the hair source meshes from guide models kept in the
gitignored `vendor_assets/`.

### Outputs

- `characters/body_a.glb`, `characters/body_b.glb`: the skeleton, the body
  split into regions (`head`, `scalp`, `ears`, `neck`, `torso`, `upper_arms`,
  `forearms`, `hands`, `hips`, `thighs`, `calves`, `feet`) at LOD0 to LOD3,
  and every animation clip.
- `<asset>_<body>.glb` for each clothing item, e.g.
  `gear/body/robe_school_house_a_body_a.glb`.
- `hair/<name>_<body>.glb` and the variant worn under hats,
  `hair/<name>_cap_<body>.glb`. Each style belongs to one body.
- `characters/broom.glb`: the broom, positioned at the rider's hips bone.
- `characters/atlas.png` (the shared 256 x 256 texture, also embedded),
  `characters/face_<body>.png` and `face_mask_<body>.png` (the painted face and
  its colour and shadow masks), and `characters/manifest.json`.

Every file carries the same 82-bone skeleton in the same joint order: `root`,
the Rigify `DEF-*` deform bones (with jaw and eyes), and the sockets
`socket_hand.L/R`, `socket_head`, `socket_back`, `socket_hip.L`. Clothing and
hair bind to the body's skeleton by bone name. Mesh nodes are named
`<name>_lod0` to `<name>_lod3` with extras (`region`, `asset`, `slot`,
`hides`, `long`, `lod`, ...). Triangle budgets per LOD are in
`charlib/pipeline.py` (`LOD_BUDGETS`): bodies at most 16,000 / 5,000 / 1,500
/ 500 triangles.

**Vertex attributes.** `_SHADE` (VEC4): baked shade, hair strand and band
phase, and an outline weight hint. `_OUTLINE` (VEC3): the inverted-hull
outline's smoothed normal times its width weight.

**Colour.** Every asset uses one material, `character`, whose base colour is
the atlas, so a dressed character merges into one draw call. `COLOR_0` is a
tint mask:

```
albedo = atlas * ((1 - r - g - b) + r * C0 + g * C1 + b * C2)
C = (skin tone, hair colour, eye colour)   on bodies
C = (hair colour, -, -)                    on hair
C = (primary, secondary, trim)             on clothing
```

Mask 0 keeps the atlas colour. Underwear is painted on, so an empty slot stays
modest. The head instead samples the painted face texture
(`charlib/face_paint.py`, `charlib/face_shadow.py`).

**Shape keys**: the creator's two-sided face sliders (`face_jaw_narrow/wide`,
`face_cheek_soft/high`, `face_nose_small/large`, `face_brow_low/high`,
`face_eyes_narrow/round`) and the expressions `blink_l`, `blink_r`, `smile`,
`frown`, `mouth_open`, `brows_up`, `brows_down`, on the head only.

**Height** is a uniform scale of the `root` bone (1.60 to 1.88 m for
`body_a`, 1.52 to 1.80 m for `body_b`), so clothing and hair follow;
locomotion clips play at `speed / (speed_mps * scale)`.

**Animations** (30 fps, baked to the deform bones, in place): `idle`, `walk`
(rate 1 at 3.0 m/s), `run` (rate 1 at 6.5 m/s), `wave`, `bow`, `sit_down`,
`sit`, `floor_rest`, `floor_sit`, `broom_ride`, `broom_hover`, and the spell
and class clips in `charlib/anim_spells.py`: `gesture_<key>` (the wand
gestures of `data/classes/gestures.json`), `cast`, `duel_ready`,
`shield_raise`, `hit_react`, `knockback`, `stun_fall`, `stun_rise`,
`disarmed`, `professor_stand`, `professor_demonstrate`, `desk_rest`,
`desk_practice`, `spectator_cheer`.

**Clothing rules.** `hides` lists the body regions not drawn under an item.
Robes are worn open over a jumper, shirt and tie that are part of the robe
item. Hats hide `scalp`; when a hat is worn the client loads the hair's `_cap`
file. Hair always hides `scalp`, and styles that fall over the ears also hide
`ears`.

## Review renders

Review renders go to `art/renders/` (gitignored); nothing reads them.

```sh
# Floor plans and views of the greybox
blender -b --factory-startup --python tools/blender/render_previews.py -- \
    [--only plan|views] [--views a,b] [--levels 0,1] [--region x0,z0,x1,z1 --tag name]

# Toon-preview stills of the castle and rooms from the exported assets
blender -b --factory-startup --python tools/blender/world/render_toon.py -- \
    [--shading toon|standard] [--hour 21.3] [--views great_hall,grounds]

# Rooms, furniture, effects
blender -b --factory-startup --python tools/blender/world/build_dorms.py -- --render --furnish
blender -b --factory-startup --python tools/blender/world/build_school.py -- --render --people
blender -b --factory-startup --python tools/blender/vfx/build_vfx.py -- --render art/renders/vfx
```

`render_toon.py` approximates the client's toon shading from
`data/art/toon_palette.json` and `data/art/lighting.json` for judging
palettes and lighting; it is not the client's shader. Its named views are in
the script (`--views-file` takes your own).

`tests/` covers the layout library, the world and room builders, the castle
kit (including determinism and the palette rule), visibility, icons, effects

fail a test when an un-kitted cell's geometry changes unexpectedly.

## What is committed under `art/`

`art/` holds only sources a build cannot make: the hair source meshes
(`art/characters/hair_meshy/*.npz`), the bodies' shape targets
(`art/characters/shape_targets/*.npz`) and their credits. What the scripts
save there (`.blend` scenes and `art/renders/`) is generated and gitignored;
[docs/art/repo-layout.md](../../docs/art/repo-layout.md) lists every file and
the command that makes it. To rebuild the `.blend` scenes for inspection:

```sh
tools/blender/build_art_blends.sh                 # world, characters, vfx (run prepare.mjs first)
tools/blender/build_art_blends.sh characters      # only art/characters/body_a.blend, body_b.blend
```

A change made by hand in a `.blend` is lost on the next build; make it in the
scripts or data.

## Changing or adding an asset

1. Change the script or data (a new piece in `castle_kit/pieces/`, a model in
   `world/furniture_models.py`, a catalog entry, a palette name, ...).
2. Run `node client/scripts/prepare.mjs` (or `bin/dev --build-assets`): only
   the steps whose sources changed rebuild. If your script reads a data file
   through a path built at run time, add that file to the step's `sources` in
   `client/scripts/asset-steps.mjs`.
3. Regenerate any [generated data files](#generated-data-files) the change
   affects, then run the tests and, for castle changes, `castle_kit/lint.py`.
4. Look at it in the client and in review renders. Keep screenshots and
   renders in `.out/` or `art/renders/`; never commit them.
5. Commit the scripts and data only. Third-party sources need a licence that
   allows redistribution (CC0 or CC BY family) and a row in
   [art/CREDITS.md](../../art/CREDITS.md).

After the change reaches `main`, a maintainer publishes the asset release for
the new fingerprint (`npm run assets:publish`).
